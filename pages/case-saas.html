02. CASE STUDY

SaaSプロダクト
多店舗の商品一元管理

プロジェクト : 多店舗経営をモデルとした商品一元管理のSaaS（自主制作）

担当範囲 : 課題整理 / UX設計 / 情報設計 / UIデザイン

概要

SaaSプロダクトのWEBアプリケーションを想定し、公式サイト・モール展開などの多店舗経営をモデルとした商品一元管理のケーススタディ。
商品情報を修正する際、多店舗経営をしていると店舗単位で作業が繰り返し発生することに注目し、店舗単位ではなく商品単位で一元管理するプロダクトを企画。
複雑な商品情報を、ユーザーが日常的に使いやすいように整理し、操作性と安全性の両立を目指しUX/UI設計を行った自主制作である。

01. OVERVIEW

TARGET USER

自社通販サイトとモール店舗を複数運営し、商品管理を行う担当者を主対象とした。 少人数運用（1〜3名）で、担当する店舗が明確に分かれておらず、 商品登録・価格変更・SKU管理・在庫管理・販売する店舗管理などを並行して担う現場を想定している。

CORE GOAL

商品情報を店舗単位ではなく、商品単位で管理できるようにし、 複数の販売店舗にまたがる更新作業の負担を減らすこと。 あわせて、変更の影響範囲や未反映状態を見える化し、 スピードと安全性の両立を目指した。

SCOPE

対象は、商品情報 / SKU / 在庫 / 販売チャネル同期 / 商品変更履歴管理。 一方で、受注管理 / 発送管理 / 顧客管理 / 売上分析 / 権限管理は対象外とし、 小規模〜中規模の通販事業者が扱いやすい範囲に絞って設計した。

MY APPROACH

実務で感じていた運用課題を起点に 「何の機能を増やすか」ではなく「何を中心に情報を持つべきか」から再設計した。 UIの見た目だけではなく、対象とするユーザー、商品自体がもつ複雑な情報構造、操作導線、対象外スコープまで含めて プロダクトとして成立する構造を考えている。 本プロダクトでは、課題整理・情報設計・UI設計まで一貫して制作している。

02. PROBLEM

■ 商品変更のたびに、各店舗で同じ作業を繰り返す必要があった

一般的な通販事業では、自社サイト・楽天・Amazon・Yahooなど複数店舗で販売することが多い。 しかし価格変更、商品説明変更、画像差し替え、在庫変更、販売終了、商品パターン追加などが発生するたびに、 各店舗の管理画面で同様の更新作業を繰り返す必要があり、運用担当者の大きな負担になっていた。

■ 管理画面が店舗単位で分かれており、担当者の実際の運用とずれていた

既存の通販サイトの管理画面は、楽天管理、Amazon管理、自社サイト管理といった店舗単位の構造が多い。 ただ実際の運用者は「この商品をどう管理するか」を基準に考えるため、 操作対象と思考対象が一致せず、画面遷移や確認の負荷が大きくなりやすい状態だった。

■ 更新漏れや価格不一致など、運用リスクが起きやすかった

複数の店舗へ同じ変更を反映する運用では、価格不一致（店舗によっては価格が異なる場合もある）、更新漏れ、商品情報の差異といった小さなズレが発生しやすい。 これらは現場の確認コストを増やすだけでなく、販売の機会損失や顧客体験の低下にもつながりうる。

■ 少人数運用では、重い権限設計より「後から追えること」が重要だった

想定ユーザーは1〜3名規模の運用であり、厳密な権限管理を先に作り込むよりも、 誰が何を変更したかを履歴で追える状態の方が現実的だと判断した。実際の現場でも、少人数制であると運営責任者との距離が近く、変更内容を直接確認しながら運用するケースが多い。 そのため、権限管理や承認フローはオプションとして追加する形をとり、スムーズな運用が成立するプロダクトにする必要があった。

03. THE INSIGHT

店舗ごとの操作ではなく、
「商品をどう管理するか」を中心に構造を組み直す。

問題は単に作業量が多いことだけではなく、運用者の思考と管理画面の構造がずれていたことだった。 そのため、操作を少し便利にするのではなく、まず、プロダクトの主オブジェクトを「商品」として再定義し、情報の持ち方から見直す必要があると判断した。

04. STRATEGIC DECISION

01. PROJECT START

出発点は、通販サイトの実務で感じていた反復作業の負担

公式サイト・モール店舗の多店舗運営を行っていると、商品情報の変更が発生すると、各販売店舗の管理画面で同じような作業を繰り返す必要がある。 さらに、変更の内容が価格や在庫、販売状態など通販事業者にとって重要な情報であるため、更新漏れや価格不一致などの小さなズレが起きないように、反映前の確認作業も増えることになり、運用担当者の負担が大きくなっていた。

02. REFRAMING THE ISSUE

運用課題を「商品中心UI」の課題へ置き換えた

各店舗の管理システムが異なるため、どうしても店舗単位で管理する既存構造となってしまうが、これは運用者の思考と一致していない。 そのため「どの店舗を触るか」ではなく「どの商品をどう管理するか」を中心に据えるOOUIの考え方を採用したプロダクトを企画。

03. DECISION MAKING

店舗単位案

各販売店舗ごとに更新し続ける

Pros: 既存の運用構造に近いため、導入が容易。

Cons: 画面遷移と重複作業が減らない。

商品中心案

商品を主オブジェクトにして複数の店舗を横断管理する

Pros: 思考と操作が一致しやすく、反復作業を減らせる

Cons: プロダクトにおいて差分管理や反映設計まで整理が必要。

多機能統合案

商品管理以外にも、受注や顧客管理まで広げる

Pros: このプロダクトだけで、幅広く通販運用をカバーできる。

Cons: プロダクトが複雑化しすぎてしまい、逆に運用者の負担になる可能性がある。また、売上情報や顧客情報まで担うことで権限管理が必要となり、運用ハードルが高くなる。

04. REASONING

機能の対象範囲を絞り、シンプルで直感的な運用が成立する構造を優先

通販事業において、商品管理以外にも受注管理や顧客管理、売上管理、分析業務など、さまざまな業務があるが、 この自主制作では、商品情報の管理に絞り、受注管理や顧客管理などは対象外とした。 これは、プロダクトの焦点を明確にし、作業の発生頻度が高い領域に対して解像度高く向き合うためである。

また、権限管理もあえてオプション機能として切り離し、小規模〜中規模EC事業者の少人数運用を前提に、変更履歴による管理を採用した。権限管理をつけることで、運用者の作業範囲の制限や管理者の承認フローが発生してしまい、スムーズな運用が阻害される可能性があると判断したためである。 理想的な多機能化よりも、実際に使える現実性を優先している。

05. FINAL DECISION

商品の一元管理とし「一覧 → 編集 → 反映」のシンプルな導線へ整理

一般的な店舗単位での管理ではなく、管理の主オブジェクトを商品に置くことで、 各店舗システムによって分断されることなく商品情報を一覧で確認できる構造を設計。 また、商品ごとの詳細な修正は、一覧画面の文脈をもったまま右スライドインの編集画面で操作することができ、確認モーダルを挟んで安心して反映させることのできる流れを想定した。 操作効率だけでなく、安全性と認知負荷のバランスも重視した。

05. DESIGN STRUCTURE

商品単位で管理することで、運用者の思考と操作を一致させる

本プロダクトでは、管理単位を「商品」とし、 商品が持つ情報、販売チャネル、商品状態、主要機能、変更履歴を整理した。 これにより、店舗ごとではなく商品ごとに状態を把握しながら更新できる構造を目指している。

商品単位で管理することによって、実際によくある「〇〇の商品を今週いっぱい割引対象にしたい」「△△の商品は終了商品につき、現在の在庫を店舗と通販で販売し切りたい」などの商品を起点とした施策にも対応しやすくなると考えている。
これらは運用者の負担を減らすだけでなく、販売機会の損失を防いだり、その先にある顧客体験の向上にもつながると考えている。

06. UI DESIGN

操作効率だけでなく、安全に更新できる体験まで設計する

この自主制作では、管理画面らしい見た目を整えることではなく、商品がもつ複雑な情報構造を、ユーザーが日常的に使いやすいように整理することを重視した。 「何を一覧で把握し、どこで編集し、どの時点で慎重さを求めるか」をUIに落とし込むことで、日常的に使いやすく、安心して更新できる体験を提供することを目指している。 特に各販売店舗への一括反映は、明確で安全性の両方が求められる領域として扱っている。

商品一覧画面

商品一覧では、価格・在庫・販売状態など、よく使う項目をその場で確認・編集できる構成とした。また、フィルター機能をつけることで、取り扱いジャンルに合わせて注視する項目をカスタマイズできるように設計。
さらに、各販売店舗の情報も確認できることで、一元的に商品情報を把握しながら、店舗ごとの差異も見失わない構造にしている。

スライドインの詳細編集画面

商品の詳細編集は右スライドイン形式を採用し、 画面一覧の文脈を維持したまま編集へ入れるようにした。 これにより、どの商品を複数選択していたか中断することなく編集を進められる。
また商品詳細では、価格や在庫などの基本情報だけでなく、各販売店舗ごとの差分も整理できる構造にしている。一元管理でありながら、チャネル差異を見失わないことを重視している。

変更時の確認モーダル表示

変更内容は即時反映せず、事前確認のフローとして確認モーダルのポップアップを採用した。 変更を反映する対象店舗と変更内容を可視化することで、 誤操作リスクと心理的不安を軽減し、安全な一括反映を支えている。

誤操作のリスクを考慮した設計

商品一覧の画面で、商品の複製や削除などの操作が一括してできる構成も検討したが、本設計ではあえて採用しなかった。これは、操作が誤りだった場合の影響を鑑みた結果、複製や削除などの操作は、慎重に判断して行うべき操作として判断した結果である。
操作性だけでなく「どの操作をどこで行うべきか」を整理することで、ユーザーが安全に運用できる体験を重視している。

変更内容の予約反映

日々の運用の中で、反映タイミングが重要なケースも多い。それを踏まえ、変更内容は即時反映だけでなく、日時を指定した予約反映にも対応している。 運用のタイミングをコントロールできるようにすることで、業務フローに合わせた更新を可能にした。
また、公開対象の店舗を個別に設定できるようにすることで、チャネルごとの戦略や状況に応じた柔軟な運用を支えている。

変更者を必須とする設計

権限管理を重く持たない代わりに、変更履歴によって「何が」「誰によって」「どのように」変わったかを追える設計を採用した。 管理者や運用者の承認フローの負荷を抑えながらも、少人数運用でも管理責任を持ちやすい状態を意識している。

TRADE-OFFS

操作性 vs 安全性

一覧画面で複製・削除まで完結できれば操作性は上がるが、 複数の販売店舗へ影響する変更では誤操作リスクも大きくなる。 そのため本設計では、重要な変更は編集画面と確認フローを経由させ、安全性を優先した。

一覧の情報量 vs 視認性

一覧に多くの情報を載せるほど一画面で把握できる情報量は増えるが、 その分、判断のしやすさは下がりやすい。 そのため価格・在庫・販売状態など優先度の高い情報を中心に表示し、 詳細は編集画面側に分ける構造とした。

07. PRODUCT SCOPE

このプロダクトでは、主オブジェクトを商品とし、 商品名、説明、画像、SKU、価格、在庫、販売状態、販売終了日、担当者情報など 商品が持つ情報を整理することを重視した。
これは、運用者が日常的に分かりやすく・使いやすく管理できる構造をつくるためである。 どの情報を商品一覧に載せるか、どの情報を編集画面に分けるかを整理することが、シンプルでスムーズな操作を実現するために重要な要素であると考えている。

また、運用者の利用シナリオも「商品一覧から対象商品を複数選択 → 商品一覧画面で同期する店舗を選択＆価格修正 → 変更確認モーダルで内容を確認 → 各販売店舗へ反映」という流れに整理し、日常業務の中で実際に起きる操作を基準に構成している。

08. EXPECTED IMPACT

運用負担を減らし、より価値の高い業務に集中できる状態をつくる

本プロダクトでは、商品変更を店舗ごとではなく商品単位で管理することにより、 作業時間削減と運用負担軽減を期待している。 あわせて、商品情報一元管理により、価格不一致、更新漏れ、情報差異といった 運用リスクの低減も目指している。

単に効率化するだけでなく、 運用担当者が商品企画、売上戦略、顧客体験改善など、 より価値の高い業務に集中できる状態をつくることもこのプロダクトの価値として位置づけている。

今後期待する効果

※実務導入前のため、想定される価値として整理している

① 作業コスト削減

商品単位で管理することで、作業時間削減と運用負担軽減が期待できる。

② 管理リスク削減

商品情報一元管理により、価格不一致・更新漏れ・情報差異といった運用リスクを抑えられる。

③ 人的リソースの最適化

運用担当者が商品企画・売上戦略・顧客体験改善など、より価値の高い業務に集中しやすくなる。

④ 顧客体験の安定化

各チャネルへの適切な反映により、販売機会損失の防止や顧客体験の安定につながる。

09. LEARNING

実務課題を、プロダクトの論点に翻訳することが重要だった。

この自主制作を通して学んだのは、 現場の不便さをそのまま並べるだけでは、プロダクトにはならないということだった。 何を主オブジェクトにするのか、どこまでを対象にし、どこからを対象外にするのか、 どの操作を速くし、どの操作を慎重にするのか。 そうした判断を重ねることで、はじめて体験の骨格が見えてくると実感した。

また、実務経験をもとにした自主制作だからこそ、 現場で成立するかという視点を最後まで持てたことも大きかった。 今後は、こうした「実務起点の課題発見」と「構造から考える設計」を、 プロダクトデザインの領域でさらに深めていきたい。
